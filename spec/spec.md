# Instructions

<p>
Build an Inventory Management web application using Vaadin Flow and Spring Boot. The app must include login and signup pages, user authentication, role-based authorization, and full CRUD views for the main inventory entities. Use PostgreSQL as the database. Configure Flyway migrations from the start, including initial SQL migration files to create all tables, relationships, constraints, and seed data.
</p>

<p>
The generated project must be easy to run locally with Docker and ready for further testing, security improvements, and operational hardening. Do not include tenant-specific modeling. Use `bigint generated by default as identity` for primary keys in PostgreSQL, which replaces the old `bigserial` style while keeping the same business intent.
</p>

## Core Application Requirements

<p>
Create a Spring Boot + Vaadin Flow application for inventory management. The application must include a clean responsive UI, authentication, signup, login, protected routes, role-based access control, list views, create views, edit views, detail views, and delete functionality for the main inventory entities.
</p>

The main entities are:

- Users
- Roles
- Resources
- Actions
- Permissions
- Categories
- Suppliers
- Products
- Stock Movements

The application must include:

- Login page.
- Signup page.
- User authentication.
- Role and permission management.
- CRUD screens for inventory entities.
- PostgreSQL database.
- Flyway migrations from the start.
- Dockerfile for the Spring Boot application.
- `compose.yml` for the application and PostgreSQL database.
- Responsive Vaadin layout.
- Built-in Vaadin Grid for list views.
- Built-in Vaadin filtering/search support where appropriate.
- Sidebar forms for create/edit operations.
- LitRenderer templates for high-quality Grid content in selected columns.
- Form validation using Bean Validation and Vaadin Binder.
- Clean package organization.

## UI Requirements

<p>
Use Vaadin Flow for all screens. Each entity should have list, create, edit, view, and delete functionality. The create/edit forms must not replace the whole page. They must appear in a dismissible sidebar panel attached to the right side of the screen. The sidebar should be usable on desktop and mobile.
</p>

<p>
The list screen should remain visible while the sidebar form is open. On smaller screens, the sidebar may cover most of the screen width, but it should still behave as a dismissible panel. Use local UI-only state where appropriate to control sidebar visibility, selected row, dirty state, filter text, and form mode.
</p>

## Local Signals Requirement

<p>
Local signals provide lightweight, UI-only state management for scenarios where state does not need to be shared across users or sessions. They are ideal for managing component-level state like visibility toggles, form state, selected grid row, active filter, or local UI preferences.
</p>

Use local signals or equivalent local UI state for:

- Sidebar visibility.
- Sidebar mode: create, edit, or view.
- Currently selected entity.
- Search text.
- Active filters.
- Local form dirty state.
- Confirmation dialog state.

Do not use local signals for:

- Authentication state.
- Persistent business data.
- Cross-user data.
- Security decisions.
- Server-side authorization.

## Vaadin Grid Requirements

<p>
Use Vaadin Grid as the primary component for list screens. Use built-in filtering and search support with `DataProvider`, repository queries, or service-level filtering. The list screens should support filtering by text and key status fields, such as active/inactive products, low-stock products, active suppliers, active roles, and movement type.
</p>

Use `LitRenderer` templates for high-quality grid content in fields such as:

- Product name and SKU.
- Product stock status.
- Product active state.
- Supplier contact information.
- User active state.
- Role system/custom badge.
- Stock movement type and quantity direction.

Example visual behavior:

- Show active/inactive as compact badges.
- Show low-stock products as a visible warning badge.
- Show positive stock movements with a plus sign.
- Show negative stock movements with a minus sign.
- Show role type as `System` or `Custom`.

## Authentication and Security Requirements

<p>
Use Spring Security with Vaadin security integration. Public routes should include login, signup, and static frontend assets. All inventory routes must require authentication. Role and permission checks should be implemented at the service layer and optionally reflected in the UI by hiding or disabling unauthorized actions.
</p>

Use a simple security configuration similar to this:

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {

  @Bean
  public SecurityFilterChain vaadinSecurityFilterChain(HttpSecurity http) throws Exception {

    http.authorizeHttpRequests(authorize -> {
      authorize
          .requestMatchers(
              "/styles/**",
              "/fonts/**",
              "/frontend/**",
              "/images/*.png",
              "/crow3-frames/**",
              "/icons/**",
              "/line-awesome/**")
          .permitAll();
    });

    http.authorizeHttpRequests(
        authorize -> authorize.requestMatchers("/share/**").anonymous());

    http.with(vaadin(), vaadinSecurity -> {
      vaadinSecurity.loginView(LoginView.class);
    });

    return http.build();
  }
}
```

The `LoginView` must:

- Use Vaadin `LoginForm` or a custom responsive login layout.
- Route unauthenticated users to the login page.
- Display invalid-login feedback.
- Provide a link to the signup page.
- Avoid exposing whether a username or email exists.

The `SignupView` must:

- Validate username, email, and password.
- Store password hashes only.
- Never store raw passwords.
- Assign a default role such as `INVENTORY_VIEWER` or `WAREHOUSE_OPERATOR` depending on the desired application policy.
- Reject duplicate usernames and duplicate emails.

## Business Rules

<p>
The database should enforce the business invariants that are safe and realistic to enforce at the database level. The application service layer should enforce workflow rules, active/inactive rules, and authorization rules. Stock movement creation must be transactional.
</p>

Required business constraints:

- A user must have a unique username.
- A user must have a unique email.
- A role must have a unique stable code.
- A resource must have a unique stable code.
- An action must have a unique stable code.
- A permission must be a unique combination of resource and action.
- A user cannot receive the same role twice.
- A role cannot receive the same permission twice.
- A category name must be unique.
- A product SKU must be unique.
- Product price cannot be negative.
- Product stock cannot be negative.
- Product minimum stock cannot be negative.
- A stock movement quantity delta cannot be zero.
- A stock movement type must be one of the approved movement types.
- Positive stock movement types must have positive quantity deltas.
- Negative stock movement types must have negative quantity deltas.
- Manual adjustments, damage, and loss movements must include a reason.
- Stock movements should be append-only from the business perspective.
- Mistakes in stock movements should be corrected by a new compensating movement, not by editing history.
- Users, roles, products, suppliers, categories, resources, actions, and permissions should generally be deactivated instead of physically deleted when they have historical usage.

    id bigint generated by default as identity primary key,

    id bigint generated by default as identity primary key,

    product_id bigint not null,
    user_id bigint not null,

    quantity_delta integer not null,

    reason text,

        foreign key (product_id)
        references product(id)
        on delete restrict,

    constraint fk_stock_movement_user
        foreign key (user_id)
        references app_user(id)
        on delete restrict,

    constraint chk_stock_movement_type
        check (
            movement_type in (
                'PURCHASE',
                'SALE',
                'RETURN_IN',
                'RETURN_OUT',
                'ADJUSTMENT_IN',
                'ADJUSTMENT_OUT',
                'INITIAL_STOCK',
                'DAMAGED',
                'LOST'
            )
        ),

    constraint chk_stock_movement_quantity_delta_not_zero
        check (quantity_delta <> 0),

    constraint chk_stock_movement_direction
        check (
            (
                movement_type in ('PURCHASE', 'RETURN_IN', 'ADJUSTMENT_IN', 'INITIAL_STOCK')
                and quantity_delta > 0
            )
            or
            (
                movement_type in ('SALE', 'RETURN_OUT', 'ADJUSTMENT_OUT', 'DAMAGED', 'LOST')
                and quantity_delta < 0
            )
        ),

    constraint chk_stock_movement_reason_required_for_adjustments
        check (
            movement_type not in ('ADJUSTMENT_IN', 'ADJUSTMENT_OUT', 'DAMAGED', 'LOST')
            or reason is not null
            and length(trim(reason)) > 0
        )
);

## Stock Movement Transaction Rule

<p>
Stock movements must be created inside a transaction. The application must update the product stock atomically and then insert the movement record. Do not read the product quantity in Java, calculate the new value, and then write it back. That pattern can break under concurrent users.
</p>

Use this pattern in the service layer:

```sql
update product
set quantity_on_hand = quantity_on_hand + :quantity_delta,
    updated_at = now()
where id = :product_id
  and quantity_on_hand + :quantity_delta >= 0;
```

Then:

- If the affected row count is `1`, insert the stock movement.
- If the affected row count is `0`, reject the operation because it would produce negative stock or the product does not exist.
- Wrap both operations in the same transaction.

Pseudo-flow:

```text
begin transaction
  atomic update product quantity
  if no row was updated, reject operation
  insert stock_movement row
commit transaction
```

## Delete Policy

<p>
Use physical delete carefully. Business records that have historical references should generally be deactivated instead of deleted. This is especially important for users, products, categories, suppliers, roles, permissions, and stock movements.
</p>

Recommended behavior:

- Products: deactivate if they have stock movements.
- Categories: delete only if unused; otherwise deactivate.
- Suppliers: delete only if unused; otherwise deactivate.
- Users: deactivate instead of delete.
- Roles: deactivate custom roles if no longer used.
- Permissions: deactivate instead of delete if assigned historically.
- Stock movements: append-only; do not allow normal delete from the UI.

## Permission Model

<p>
Use normalized RBAC. Do not store permissions as JSON arrays inside roles. A permission is defined as a unique pair of resource and action.
</p>

Examples:

```text
PRODUCT:CREATE
PRODUCT:READ
PRODUCT:UPDATE
PRODUCT:DELETE
STOCK_MOVEMENT:CREATE
STOCK_MOVEMENT:READ
USER:CREATE
ROLE:ASSIGN
REPORT:EXPORT
```

Authorization rule:

```text
A user is allowed to perform an action on a resource if at least one of the user's active roles has an active permission for that resource and action.
```

Service-layer permission query:

```sql
select exists (
    select 1
    from app_user u
    join user_role ur on ur.user_id = u.id
    join role ro on ro.id = ur.role_id
    join role_permission rp on rp.role_id = ro.id
    join permission p on p.id = rp.permission_id
    join resource r on r.id = p.resource_id
    join action a on a.id = p.action_id
    where u.id = :user_id
      and u.active = true
      and ro.active = true
      and p.active = true
      and r.active = true
      and a.active = true
      and r.code = :resource_code
      and a.code = :action_code
);
```
